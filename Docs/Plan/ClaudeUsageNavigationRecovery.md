# Claude 사용량 설정 경유 복구

## 목표와 범위

- 합성 WebView2에서 `/settings/usage`의 302 → 동일 출처 `/settings` → 같은 문서의 사용량 라우트 → 200 흐름을 재현한다. 탐색 실패 기록만으로 실계정에서 어떤 경로를 거쳤는지는 알 수 없다.
- 현재 최상위 프레임과 로더에 속한 초기 `/settings`만 기존 30초 한도에서 기다린다. 사용량 페이지와 현재 시도의 새 응답이 모두 확인되어 정규화 캐시를 교체한 뒤에만 성공한다.
- 별도 경유 경로, 새 로더의 사용자 탐색, 로그인/접근 오류, 반복 갱신, 타임아웃·재시도 및 종료 경계를 검증한다. 요청 수집 범위와 인증·진단·Codex 흐름은 변경하지 않는다.

## 영향 파일과 검증

- `ClaudeConnectionWindow.cs`: 문서 판정과 응답 처리 경계.
- `Tools/Test-ClaudeRefreshReliability.ps1`, `Tools/Test-UsagePacing.ps1`: 등록 소스/HTML 검사, 기존 DLL 회귀, 임시 프로필 WebView2 탐색 fixture. 요청은 가로채고 외부 통신은 차단한다.
- 이 문서와 `README.md`: 검증 방법과 실행 결과. 원본 응답·계정·사용자 경로는 남기지 않는다.

## 검증 결과

- 변경 전 탐색 판정으로 실행했을 때 합성 WebView2가 302, 같은 문서의 사용량 경로, 새 200 응답에 모두 도달했으나 `NavigationFailed`가 남고 캐시는 교체되지 않았다.
- 변경 후 같은 흐름에서 새 정규화 캐시 교체와 `Success`를 확인했다. 첫 탐색, 동일 URL 및 프래그먼트 상태에서 재탐색도 통과했다.
- 설정 화면 자체 또는 하위 프레임의 200, 다른 로더와 출처, 미승인 경로, 사용자 경로 변경, 로그인 리디렉션·403, 30초 타임아웃 전후 응답과 종료를 확인했다. 네트워크 실패 뒤 자동 재시도, 429/503의 `Retry-After`, Codex 독립 갱신 소스 검사도 통과했다.
- PowerShell 7 소스/HTML 32건, Release 빌드(경고·오류 0개), Claude 중심 실제 DLL 합성 검사 240건(격리 탐색 및 팝업 렌더링 포함)을 할당된 작업 트리에서 통과했다. 실계정에 접속하지 않았다.
