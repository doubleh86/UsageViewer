# Claude 사용량 갱신 안정화

작성일: 2026-11-19

상태: 기획 작성 완료 · 구현 전

## 목표

Claude가 잠깐 조회되지 않아도 이유를 알 수 있고, 복구 가능한 오류는 앱이 스스로 재시도한다.
사용자 확인이 필요한 경우에만 연결 창을 열도록 안내한다. 오래된 값을 최신 사용량으로 표시하지 않는다.
기존 작은 상단 바와 상세 화면을 유지하며, 상태 확인 때문에 화면이 커지거나 알림이 반복되지 않게 한다.

## 확인된 현상과 원인 확인 범위

- 사용자는 Claude 영역에 ‘갱신 필요’가 반복 표시되는 현상을 제보했다.
- 직전 읽기 전용 확인에서는 웹 사용량 캐시가 새로 수신됐고 리셋 시각도 지나지 않았다.
  지속적인 로그인 실패나 한도 만료가 실제 원인이었다고 단정할 근거는 없다.
- 현재 `TopUsageBar.CreateMetric`은 조회 오류, 15분 초과 미수신, 이전 값 상태를 모두 ‘갱신 필요’로 표시한다.
- `ClaudeConnectionWindow`는 연결된 공식 사용량 페이지를 다시 탐색하고, 해당 페이지의 사용량 응답을 관찰한다.
  페이지 탐색을 요청한 것과 새 사용량을 수신한 것은 서로 다른 결과다.
- 현재는 200이 아닌 사용량 응답을 모두 로그인 확인 안내로 처리한다. 탐색 실패와 사용량 응답 미수신을
  별도로 추적하지 않으며, 탐색 요청부터 실제 사용량 수신까지를 묶는 단일 진행 상태와 제한시간도 없다.
- 로그인 만료, 네트워크 문제, 요청 제한, 페이지 응답 변경, 숨김 웹뷰의 동작 차이는 조사할 후보이다.
  이번 현상의 확정 원인으로 기록하지 않는다.

기존 연결 방식은 [작은 복수 제공자 팝업 계획](CompactMultiProvider.md)의 Claude 데스크톱 사용자 연결을 따른다.

## 사용자에게 보이는 상태

상단 바의 너비는 264 DIP로 유지한다. 마지막 정상 값의 유효성과 조회 진행 상태를 따로 관리한다.
아래 문구는 기본안이며, 긴 문구는 상세에만 표시한다. 상단 바의 긴 마우스오버 툴팁은 다시 추가하지 않는다.

| 상황 | 상단 바 | Claude 상세의 안내 | 다음 동작 |
| --- | --- | --- | --- |
| 정상 수신 | 기존 `5h 97%` 등 | 기존 한도·리셋 시간 | 정상 주기로 확인 |
| 새 값을 받는 중 | 유효한 직전 값 + 작은 갱신 표시, 값이 없으면 `조회 중` | `사용량 확인 중…` | 요청 완료 또는 제한시간까지 대기 |
| 일시적인 조회 실패, 직전 값은 유효 | 직전 값 + 주의 표시 | `일시 오류 · 마지막 수신 HH:mm` | 자동 재시도 |
| 정상 수신 후 15분 초과 | `갱신 지연` | `마지막 수신 HH:mm · 재시도 중` | 자동 재시도, 이전 값은 이전 값으로 구분 |
| 로그인 확인 필요 | `로그인 확인` | `연결 창에서 로그인 상태를 확인해 주세요.` | 사용자 클릭으로 연결 창 열기 |
| 접근 거절·추가 확인 | `접근 확인` | `Claude 페이지에서 접근 상태를 확인해 주세요.` | 사용자 클릭으로 확인, 자동 우회 금지 |
| 요청 횟수 제한 | `잠시 대기` | `요청 제한 · 잠시 후 다시 확인합니다.` | 서버 대기시간 준수 |
| 응답 해석·한도 정보 확인 실패 | `응답 확인` | `사용량 정보를 확인하지 못했어요.` | 제한된 재시도 후 사용자 확인 |
| 리셋이 지난 한도 | 유효한 다른 한도가 있으면 해당 값, 없으면 `갱신 중` | 해당 행에 `초기화 후 새 값 확인 중` | 새 응답으로만 비율 확정 |

- 직전 값을 표시할 때 주의 표시와 상세 안내를 함께 제공해 정상 최신 값으로 오해하지 않게 한다.
- 갱신 지연·인증 오류·접근 거절 상태는 직전 값을 정상처럼 상단에 남기지 않는다.
- 이전 수치가 남아 있어도 조회 실패 상태를 해제하지 않는다. 새 유효 응답을 받은 뒤에만 해제한다.
- 실패·미제공·리셋 경과를 0%나 100%로 바꾸지 않는다. 실제 0%는 기존 한도 소진 표시를 유지한다.
- 연결 안내는 재로그인이 필요한 상태에서만 강조한다. 일시 오류에 매번 ‘다시 연결’을 권하지 않는다.
- 정상 복구 시 안내를 조용히 해제한다. 상태 변화에 사이렌·반복 토스트를 추가하지 않는다.

## 갱신과 복구 규칙

### 한 번에 한 요청

- 자동 타이머, 상세 새로고침, 트레이 새로고침은 하나의 Claude 갱신 흐름을 공유한다.
- 이미 갱신 중이면 같은 작업을 기다리며 새 탐색이나 대기 요청을 쌓지 않는다.
- 초기화와 탐색·응답 대기를 구분한다. 초기화 제한은 60초, 초기화 후 한 번의 갱신 제한은 30초를 기본안으로 한다.
- 공식 사용량 페이지의 로드 완료만으로 성공 처리하지 않는다. 사용량 응답의 파싱과 정규화 캐시 저장까지
  완료되어야 정상 수신으로 처리하며, 수신 시각을 바꾸는 근거도 이 성공으로 한정한다.
- 시도 식별자를 사용해 종료·취소된 이전 시도의 늦은 성공/오류가 새 상태를 덮어쓰지 못하게 한다.
  실제 응답은 원래 연결한 제공자·현재 시도의 대상인지 검증하고, 순서를 확인하지 못하면 새 성공으로 채택하지 않는다.
- 연결 창에서 사용자가 로그인 중이면 자동 탐색하지 않는다. 이를 시간 초과나 로그인 실패로 집계하지 않는다.
  사용자가 누른 새로고침과 페이지에서 직접 수신되는 사용량은 처리한다.
- 앱 종료 시 타이머·대기·후속 재시도를 취소한다. 종료 뒤 콜백은 UI나 캐시를 갱신하지 않는다.

### 실패별 처리

| 근거 | 분류와 처리 |
| --- | --- |
| HTTP 401 또는 실제 로그인 화면으로 이동한 사실 | 로그인 확인 상태로 전환하고 자동 재시도 중단. 사용자 연결 후 정상 수신 시 재개 |
| HTTP 403 | 접근 확인 상태. 로그인 만료로 단정하지 않고 자동 반복 탐색·보안 확인 우회 금지 |
| HTTP 429 | 요청 제한 상태. 유효한 `Retry-After`가 있으면 그 전에는 수동 새로고침도 중복 요청하지 않음 |
| 네트워크·탐색 실패, 사용량 응답 대기 초과, HTTP 5xx | 일시 오류 또는 갱신 지연으로 구분하고 재시도 |
| 잘못된 JSON·예상 필드 누락·지원 범위 초과 응답 | 응답 확인 상태. 2분 뒤 한 번 재확인하고 반복되면 자동 재시도 중단. 원본 없이 원인 코드만 기록 |
| 한도 캐시 읽기·쓰기 실패 | 로컬 저장 오류로 구분. 새 수신 성공으로 표시하지 않고 기존 파일 보존 |

- 정상 갱신은 기존 60초 주기를 유지한다. 일시 오류 후 재시도는 30초 → 2분 → 5분 간격을 기본안으로 한다.
  연속 실패 시 빠른 반복을 멈추고 최대 5분 간격으로 확인한다. 유효한 서버 대기 지시는 이 간격보다 우선한다.
- 정상 타이머가 재시도 대기시간을 우회하지 못하게 한다. 수동 요청은 일시 오류의 대기를 앞당길 수 있지만
  진행 중 요청, 서버 요청 제한, 사용자 로그인 입력을 중단시키지 않는다.
- 재로그인·접근 확인·응답 확인 상태에서는 연결/확인 동작을 사용자가 선택한다. 연결 창은 자동으로 띄우지 않는다.
- 인증 확인 상태에서도 사용자가 연 연결 창에서 새 유효 응답을 받으면 즉시 정상으로 복구한다.
- 웹 캐시가 오래됐다는 이유만으로 다른 계정일 수 있는 Claude Code 캐시로 자동 전환하지 않는다.

## 기존 기능과 데이터 보호

- Codex 조회, 5시간·주간 한도 구분, 주간 막대 `|`, 오늘/내일 권장량 공식은 바꾸지 않는다.
- Claude 갱신 실패가 Codex 새로고침이나 다른 제공자 표시를 막지 않게 한다.
- 최신성·조회 성공 여부는 현재 권장량 및 잔여량 경고 판단에 함께 전달한다. 유효하지 않은 값으로
  권장량을 지급하거나 차감하지 않고, 새로운 저사용량 경고·사이렌도 발생시키지 않는다.
- 정상 캐시는 기존 정규화 사용량 필드만 유지한다. 인증 파일·토큰·쿠키를 직접 읽거나 복사하지 않는다.
  기존 WebView2 프로필의 관리는 WebView2에 맡기며 로그인 자동화나 모델 호출을 추가하지 않는다.

### 원인 확인용 최소 기록

- 재발했을 때 구분할 수 있도록 시각, 단계, 결과 코드, HTTP 상태 코드, 경과시간, 연속 실패 횟수만 기록한다.
- 정상 주기마다 기록하지 않고 실패·복구 등 상태 변화만 로컬에 최대 100건/64 KiB, 24시간 동안 보관한다.
  서버 대기 지시 값은 재시도 계산에 필요한 범위로만 사용한다.
- 원본 응답, 요청 URL/조직 ID, 계정 정보, 헤더, 쿠키, 토큰, 로컬 절대 경로, 예외 원문은 저장하지 않는다.
- 진단 파일은 Git 제외하고 릴리즈 ZIP에 포함하지 않는다. 진단 저장 실패로 조회나 UI가 중단되지 않게 한다.

## 구현 범위와 작업 순서

1. `Services/`에 Claude 갱신 상태·단일 요청·제한시간·재시도 정책을 작은 단위로 분리한다.
   상태와 시각을 합성 입력으로 검증할 수 있게 하고, 새 외부 의존성은 추가하지 않는다.
2. `UI/ClaudeConnectionWindow.cs`에서 탐색 결과·사용량 수신·HTTP 분류를 위 상태 흐름에 전달한다.
3. `TrayApplicationContext.cs`의 자동/수동 갱신을 통합하고 `UI/UsagePopup.cs`의 제공자 상태와 JSON을 맞춘다.
4. `UI/TopUsageBar.cs`, `UI/Popup.html`에 짧은 상태 표시를 적용한다. `Services/ClaudeUsageStore.cs`와
   `ClaudeWebUsageParser.cs`는 필요한 오류 구분에 한해 수정한다.
5. `Tools/`의 반복 실행 가능한 합성 검증과 README의 연결/복구 안내를 갱신한다.
   진단 기록 파일의 제외 규칙과 ZIP 구성 검증도 함께 확인한다.

## 검증 및 완료 기준

- 합성 시각·응답으로 정상 수신, 무응답, 탐색 실패, 401/403/429/5xx, 응답 형식 오류와 저장 실패를 확인한다.
- 초기화/응답 제한시간, 중복 트리거, 지연된 이전 응답, 종료 취소, 정상 복구 시 오류 해제를 검증한다.
- 재시도 간격과 서버 대기시간을 실제로 오래 기다리지 않고 제어 가능한 시계로 검증한다.
- 유효 직전 값/15분 경계/리셋 경과/실제 0%/한도 미제공을 구분하고 오류를 성공 비율로 만들지 않는지 확인한다.
- 연결 창에서 로그인하는 동안 자동 탐색이 없고, 새 수신 전에는 로그인 성공만으로 갱신 성공을 표시하지 않는다.
- Codex 독립 갱신과 권장량·경고의 실패/오래됨 처리 회귀를 확인한다.
- 임시 프로필과 합성 데이터로 264/280/320 DIP, Codex/Claude 탭과 함께 보기의 문구·가로 잘림을 검증한다.
  실제 사용자 앱·계정과 분리하고 Computer Use는 하지 않는다.
- 빌드는 후속 명시 요청 시 최소 Release 빌드와 실제 DLL 검증을 수행한다. ZIP·실행 교체·push도 별도 요청으로 구분한다.
- 실계정에서는 사용자가 직접 연결한 뒤 자동 갱신·일시 단절 후 복구·재로그인 안내를 확인한다.
  구현/합성 검사/빌드/실제 수신/사용자 화면 확인을 각각 기록하며, 구현으로 아직 확인하지 않은 재발 원인을 확정하지 않는다.

완료 기준은 ‘갱신 필요 문구를 숨겼는가’가 아니라, 이유를 구분하고 안전하게 복구하며 이전 값을 최신으로 가장하지 않는가이다.
